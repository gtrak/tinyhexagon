## Why

The repo is a verified Rust port of Open Hexagon. The product is now
**tinyhexagon**: a kid-friendly edition for players who cannot read and have
no video-game literacy. The adult menu/online/replay/Steam/Discord surfaces
are retired; the simulation, Lua content system and cross-platform renderer
are kept and altered.

The port's engineering record is kept but summarized for the new direction;
the C++ reference tree and parity tooling are retired (git history keeps
them). The fork and the original Rust port will move independently, so the
upstream relationship is tracked explicitly by an agent skill and a changelog
whose top SHA is the high-water mark.

---

## What

A single game, **tinyhexagon**:

- No menus, no text, no scores, no fail screen, no profiles, no persistence.
- Hold left/right to rotate. Fullscreen and reset are the only other
  controls. Touch halves + two corner icons on mobile/web.
- Collisions are soft: the wall bursts, the screen flashes, the world slows,
  the music ducks, and play continues. No death, no lost stage.
- A run escalates slowly over **20 stages × 30 s = 10 minutes**, then holds
  at the plateau. Each stage is the checkpoint. A new run always starts at
  stage 0.
- Generated music via `rust-synth`; colours and pulse respond to the music;
  music reacts to stages and collisions. Gentle SFX via the existing audio
  assets.
- Linux, Windows, **Android** and **wasm/emscripten** are first-class and
  packaged; tagged releases keep their GitHub workflows with renamed
  artifacts.
- The engine is altered, not rewritten; the existing cross-platform renderer
  is reused.

Non-goals: adult menus, online, Steam, Discord, workshop, servers, replays,
profiles, scores, level editor, 180° swap, text.

## Shared design details

### 10-minute escalation arc

20 stages × 30 s = 600 s. The stage index starts at 0 every run. The intro
(first ~3 s) is part of stage 0.

| Stage | Time | Difficulty mult | BPM | Music layers | Level |
|---|---|---|---|---|---|
| 0 | 0:00 | 0.55 | 70 | pad, drone | meadow |
| 2 | 1:00 | 0.61 | 73 | + pluck | meadow |
| 5 | 2:30 | 0.70 | 77.5 | + bell | river |
| 8 | 4:00 | 0.79 | 82 | + bass pulse | river |
| 11 | 5:30 | 0.88 | 86.5 | + shimmer | stars |
| 14 | 7:00 | 0.97 | 91 | + heartbeat | stars |
| 17 | 8:30 | 1.06 | 95.5 | + supersaw (all 8) | meadow |
| 20 | 10:00 | 1.15 | 100 | all 8 | plateau |

- `difficulty = 0.55 + 0.03 * min(stage, 20)`.
- `bpm = 70 + 1.5 * min(stage, 20)`.
- Level changes every 2 stages, cycling meadow → river → stars.
- Base hue advances +47° every 6 stages (about every 3 minutes); the bar
  phase adds a slow drift.
- After stage 20: no further difficulty/tempo/layer increase. Palette and
  pattern variation may continue; the run does not end.
- The values are starting points; tuning lives in one table in
  `th-app/src/journey.rs` and is refined in Issue 09.

### Soft collision

- On overlap, the offending wall is killed/burst, `status.flash_effect` is
  set, and a `bump` event is recorded.
- The app applies `timescale ≈ 0.35` for ~0.35 s, ducks the music, and plays
  a gentle bump SFX.
- No death, no state change, no restart, no progress loss. The stage timer
  continues.

### Controls

| Input | Action |
|---|---|
| Left/Right (hold), A/D | Rotate |
| F11 / F | Fullscreen (desktop) |
| R | Reset current stage |
| Esc | Quit (desktop/web) |
| Touch left/right half (hold) | Rotate |
| Touch top-left icon | Reset |
| Touch top-right icon | Fullscreen |
| Mouse: same as touch; keyboard fallback | |

### SFX

Via `th-audio` and the shipped `_RELEASE/Assets` OGGs:

| Event | Sound |
|---|---|
| Start / stage-up | `go.ogg` / `increment.ogg` (or `levelUp.ogg`) |
| Collision | soft `beep.ogg` (music duck underneath) |
| Reset | `restart.ogg` |
| Icon tap | `select.ogg` |
| Fullscreen | `beep.ogg` |

Web: both `th-audio` (OpenAL) and `th-synth` (WebAudio) start/resume on the
first user gesture.

### No persistence

- No `config.json` writes; the kid app uses `Config::default()` plus explicit
  kid settings, or reads the shipped config once as read-only defaults.
- No `Profiles/`, no `Replays/`, no `NullProfiles` writes, no IDBFS, no
  localStorage. Every run starts at stage 0.
- The web shell's persistence glue is removed.

### `th-additions` — elaboration and decision

`oh-additions` is 1,657 lines / 5 modules, built for the adult port:

- `touch_overlay.rs` (1,242 lines): an 8-button adult overlay (rotate CCW/CW,
  focus, swap, replay, restart, pause, exit), per-button refcounting, pointer
  capture, and key-icon drawing with fonts/textures.
- `input_injection.rs` (95): applies overlay press edges into the adult game's
  `Tid` bodies and the menu's `exit_action`.
- `soft_input.rs` (123): the IME/soft-keyboard controller (`WebIme`), only
  needed for text entry.
- `fullscreen.rs` (158): the web `#fs` install / browser Fullscreen API sinks.
- `lib.rs` (39): the boundary-contract docs (the retired ratchet).

Dependencies: `th-math`, `th-render`, `th-game`, `th-menu`, `th-config`, and
`web-sys` on emscripten.

What tinyhexagon actually needs: two hold zones (left/right screen halves),
two edge-anchored icons (reset/fullscreen), the browser fullscreen install,
and a pointer/touch feed. No focus/swap/action row, no menu injection, no
text entry.

**Decision: remove `th-additions`.** Salvage `fullscreen.rs` by moving its
install into the `th-app` web module (or reimplement the two DOM calls in the
shell), and implement the kid touch mapping in `th-app` from the existing
`Window` touch/pointer feed (about 50–100 lines). Keeping the crate would mean
deleting most of its modules, dropping `th-menu`, and rewriting the overlay
for two zones — more churn than removal, and it leaves adult UI in the tree.
This is the recommended default; say if you want it kept instead.

## Execution protocol

The orchestrator (this session) plans, checks upstream, dispatches, runs the
gate and commits; it does not implement.

| Role | Agent | Context | Model | Job |
|---|---|---|---|---|
| Orchestrator | this session | — | session | specs, upstream check, dispatch, gate, commit |
| Worker | `worker` | `fresh` | `local/local` | one issue per dispatch |
| Reviewer | `reviewer` | `fork` | inherits session | verdict after each impl step |
| Executable gate | orchestrator (optionally `gate-reviewer`) | — | — | re-run gate + target checks |

Per issue:

1. Upstream check (`tools/upstream-status.sh`).
2. Write `.agents/tasks/issue-NNN-impl.md` (self-contained; includes the HWM
   and `FEED-FORWARD.md`).
3. Dispatch one fresh `worker` (`local/local`, one writer).
4. Orchestrator runs `tools/gate.sh` + the issue's target checks.
5. Dispatch the forked `reviewer` with the issue, report, diff, gate output
   and HWM. It returns exactly one `VERDICT: PASS` or
   `VERDICT: BLOCKING -- <must-fix list>`.
6. Fix loop with a fresh worker on BLOCKING; re-gate/re-review.
7. On PASS: commit with the issue id, verdict, gate result and HWM; update
   the report, the issue status, and the changelog/HWM if upstream work
   landed.
8. **Feed forward:** append accepted deviations, API changes and lessons to
   `.agents/plans/002-tinyhexagon/FEED-FORWARD.md`, and update the affected
   later issue files and the next task spec. The reviewer checks that the
   feed-forward is applied. The plan is living, not frozen.

Rules: skills are truth; the orchestrator never trusts a worker's summary
without re-running the gate; one writer per worktree; no silent model or
scope substitutions; delete retired tests rather than weakening them.

## Feed-forward rule

`.agents/plans/002-tinyhexagon/FEED-FORWARD.md` is a living document. After
every landed issue the orchestrator records:

- accepted deviations from the issue contract;
- new APIs, renamed files, removed features;
- surprises/risks that affect later issues;
- changes to the upstream mapping.

The affected later issue files are updated in the same pass, and each new task
spec starts with the current feed-forward notes. This is how a fresh worker
on a later issue gets the lessons of the earlier ones without re-reading the
whole history.
